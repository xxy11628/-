# 超声上位机（UltrasoundHost）——写给新人的架构与目标说明书

> 这份文档尽量不用专业术语。读完你应该能回答：
> 这个软件是干什么的？由哪几块组成？数据怎么从板卡走到屏幕？我们为什么这样设计？现在做到哪一步了？新人从哪里开始看？

---

## 0. 一句话记住

**内核很小，插件很大；依赖只能朝契约方向；数据帧"借了要还"；判伤丢帧必须记账；换板卡只换插件。**

---

## 1. 这个项目是做什么的

这是一套**超声探伤/成像上位机软件**：电脑通过串口/网口控制超声板卡，接收板卡采到的回波数据，做处理（比如找闸门内的峰值）、在界面上画 A 扫波形和闸门表格，并判断"这一帧有没有缺陷"。

现在它主要运行在 **Windows + WPF** 上，也有一个无界面的命令行版本；板卡暂时用**模拟器**代替，真实板卡的协议正在做（M3）。

### 1.1 我们要达成的目标

| # | 目标 | 为什么 |
|---|---|---|
| 1 | **没有板卡也能开发** | 先用模拟器把整条链路跑通，板卡到了只换数据源 |
| 2 | **换板卡不改内核** | 设备是插件；新板卡 = 新插件，不动 Core/Application/界面 |
| 3 | **每一帧都有去向，丢帧可解释、可告警** | 探伤软件漏一帧可能漏一个缺陷，不能"悄悄少一帧" |
| 4 | **界面卡顿不拖累判伤** | 显示可以丢旧帧；判伤和记录不允许无声丢帧 |
| 5 | **为以后留路** | 相控阵、TFM、主机/GPU 波束合成、多板卡、记录回放，接口先留好 |
| 6 | **可测试、可维护** | 规则用测试和编译门禁守住，新人不容易"放错位置" |

### 1.2 它不是什么（避免误解）

- 不是微服务/前后端分离：**单机、单进程、模块化单体**，因为超声数据量大、延迟敏感，进程内传帧最快；
- 不是板卡驱动：驱动/固件在板卡那侧，我们做的是上位机协议与数据面；
- 不是通用插件平台：先解决超声这一个领域的问题，插件机制够用就行；
- 不是"AI 自动判伤"：当前判伤是闸门峰值这类可解释算法。

## 2. 一张图看懂架构

```
┌──────────────────────────────────────────────┐
│  App.Wpf（中文界面）      App.Cli（无界面）   │  ← 前台/总装厂：唯一认识所有插件的层
└───────────────┬──────────────────────────────┘
                │ 引用
┌───────────────▼──────────────────────────────┐
│  Application（会话/分发/计数/参数历史/取数）   │  ← 调度中心：一次采集怎么跑
└───────────────┬──────────────────────────────┘
                │ 引用
┌───────────────▼──────────────────────────────┐
│  Core（插件宿主：启动、状态、故障隔离）        │  ← 插线板/物业：管理插件
└───────────────┬──────────────────────────────┘
                │ 引用
┌───────────────▼──────────────────────────────┐
│  Contracts（契约：公共接口与数据类型）         │  ← 插座标准：大家都认它
└───────────────▲──────────────────────────────┘
                │ 只引用 Contracts（单向！）
┌───────────────┴──────────────────────────────┐
│  Plugins.Device.* / Processing.* / View.*     │  ← 电器：设备、算法、视图
└──────────────────────────────────────────────┘
```

三条铁律：

1. **箭头只能朝一个方向**：上层可以依赖下层，下层绝不能反过来依赖上层。
2. **插件只认 `Contracts`**：插件不引用 Core/Application/UI，也不互相引用（需要别的插件时，在清单里按 Id 声明依赖）。
3. **只有 `App.*` 认识所有插件**：WPF 和 CLI 是"总装厂"，负责把插件装起来；其他层不认识具体插件。

## 3. 每个项目是干什么的

| 项目 | 小白版说明 | 关键内容 |
|---|---|---|
| `UltrasoundHost.Contracts` | **公共语言/插座标准**：所有层共用的接口和数据类型 | 插件接口、帧、参数、能力、视图描述、贡献接口 |
| `UltrasoundHost.Core` | **插件宿主/物业**：按清单校验、排序、启动、停止插件，记录状态，隔离故障 | `PluginHost`、插件生命周期、`GetActive<T>()` |
| `UltrasoundHost.Application` | **调度中心**：一次采集的会话，负责打开设备、启动/停止、分发帧、计数、记参数版本、给界面取数 | `ShellSession`、`FrameFanout`、`LossCounters`、`ParameterHistory`、`FrameSnapshot` |
| `UltrasoundHost.App.Wpf` | **前台/界面**：中文 WPF 界面，A 扫波形、闸门表格、状态栏 | `MainWindow`、`AscanPlot` |
| `UltrasoundHost.App.Cli` | **无界面版本**：跑固定帧数、打印结果，用于自动化/排查 | `Program.cs` |
| `Plugins.Device.Simulator` | **模拟板卡**：没硬件时产生假数据 | 回波、噪声、通道数、ADC 位数、故障注入 |
| `Plugins.Device.SerialUdp` | **真板卡协议**：串口下命令 + 网口收数据；目前是回环模式 | 协议编解码、回环假板卡、设备插件 |
| `Plugins.Processing.Basic` | **判伤算法**：在闸门区间里找峰值，判断是否触发 | `GatePeakProcessor` |
| `Plugins.View.Basic` | **视图声明**：告诉界面"A 扫需要哪些数据"，不碰 WPF | `ViewDescriptor` + `DisplayNeeds` |
| `UltrasoundHost.Tests` | **守门员**：单元测试、架构规则测试、插件契约套件、协议往返测试 | 168 个测试 |

注意：**插件项目里没有 WPF**，视图插件只返回"描述符"，真正的控件在 `App.Wpf`。这样以后换 UI 技术、或做无界面测试，都不用改插件。

## 4. 六个核心概念（用生活比喻）

### 4.1 契约（Contracts）＝ 插座标准

所有层都依赖 `Contracts`，就像所有电器都按同一个插座标准做插头。契约里只有**接口和数据类型**，没有实现。

契约的规则：**只增不改**。今天加一个可选字段可以，明天把字段改名/删掉不行——否则所有插件都要跟着改。所以有版本号（当前 0.3.0）和公共 API 快照测试。

### 4.2 插件（Plugin）＝ 电器

每个插件都有"铭牌"（`PluginManifest`）：

- `Id`：唯一名字，比如 `device.simulator`、`processing.gate-peak`；
- `Kind`：种类（设备/处理/视图/存储……）；
- `Version`：插件自己的版本；
- `DependsOn`：依赖哪些插件（按 Id）；
- `DeviceProvides`：如果是设备，它提供什么能力（通道数、采样率、ADC 位数……）。

插件分三类：

| 种类 | 作用 | 现有例子 |
|---|---|---|
| Device | 产生数据（真实板卡/模拟器/回放） | 模拟器、串口+网口 |
| Processing | 处理一帧数据（滤波、找峰值、……） | 闸门峰值 |
| View | 声明"我想显示什么、需要多少数据" | A 扫、闸门表 |

### 4.3 宿主（Core）＝ 插线板 + 物业

宿主负责：

- 校验插件铭牌、按依赖排序启动；
- 记录每个插件状态：`Running`（正常工作）、`Faulted`（坏了）、`Rejected`（不允许启动）等；
- **故障隔离**：一个插件初始化失败，不会让整个软件崩溃；
- 提供 `GetActive<T>()`：只返回**正在运行**的插件的贡献。

> 为什么强调"正在运行"？假设判伤插件启动到一半坏了，但它已经注册的服务还在容器里；如果界面还去拿它的处理器，就会用到坏的东西。`GetActive` 把"坏插件"挡在外面。

### 4.4 Application ＝ 调度中心/后厨

界面不直接碰帧、不直接开设备。它只调用 `ShellSession`：

- 初始化宿主、打开设备、做会话检查；
- 下发参数（带版本号）、启动/停止采集；
- 把设备送来的帧**分发**给判伤/记录/显示三条路；
- 记录每一帧的去向（处理/丢弃原因）；
- 按界面"点菜"（显示需求）拷贝快照给 UI。

### 4.5 App.* ＝ 总装厂/前台

`App.Wpf` 和 `App.Cli` 是**组合根**：整个仓库里只有它们能写"装配清单"（把哪些插件装进去）。它们是唯一允许引用 `Plugins.*` 的层。

WPF 负责中文界面和绘制；CLI 负责无界面运行、自动化验证。两者共用同一个 `Application`，所以行为不会"界面一套、命令行一套"。

### 4.6 贡献接口 ＝ 电器的插头类型

插件实现不同"插头"：

| 贡献接口 | 谁实现 | 界面/会话怎么拿 |
|---|---|---|
| `IDeviceFactoryContribution` | 设备插件 | `GetActive<IDeviceFactoryContribution>()` |
| `IProcessorContribution` | 处理插件 | `GetActive<IProcessorContribution>()` |
| `IViewContribution` | 视图插件 | `GetActive<IViewContribution>()` |

界面**不能**直接遍历 DI 容器找处理器/视图，必须走 `GetActive`（架构规则 R11，有测试守着）。

## 5. 数据面的五个关键词

| 词 | 大白话 | 对应类型 |
|---|---|---|
| 帧（Frame） | 一帧超声数据，像一张小照片；其实是一块池化内存 | `AcquisitionFrame` |
| 池化/借还 | 内存从池子里"借"出来，所有人用完必须"还"；最后一个还的人真正归还 | `Rent` / `Retain` / `Dispose` |
| 序号（Sequence） | 设备给帧编号，同一轮采集严格 +1；跳号说明中间丢了 | `Sequence`、`FrameFlags` |
| 参数版本 | 采集参数像"配方"，每改一次版本 +1；帧自带它出生时的配方版本 | `ParamVersion`、`ParameterHistory` |
| 丢帧计数 | 记账本：收到多少、每条路处理多少、丢了多少、为什么丢 | `LossCounters` |

帧上有 ADC 位数、时间戳、采样率、帧标志等事实；处理器算幅度时用 `Adc.FullScaleCounts` 换算，不写死 32768。

## 6. 一次采集从点击到屏幕

```
用户点“打开”
  → ShellSession 打开设备插件
  → 会话检查（设备能力/视图是否匹配）
用户点“开始”
  → 参数先登记到 ParameterHistory，再下发设备
  → 设备插件后台开始采帧
设备采到帧
  → 写入通道（Channel）
FrameFanout（唯一读者）
  → 检查序号/溢出标志，记账
  → Retain 后分发给：判伤路径、记录路径（预留）、显示路径
判伤路径
  → 用帧自带参数版本查历史 → 处理器算闸门峰值 → 触发/告警
  → 队列满 = 欠帧，会话变“检测不完整”
显示路径
  → 按活动视图的 DisplayNeeds 拷贝快照（可选通道、保峰值抽取、30Hz 节流）
  → UI 定时器取最新快照绘制
用户点“停止”
  → 停设备 → 排空队列 → 输出最终计数
  → 检查“未归还帧数 = 0”
```

关键点：

- **判伤不依赖显示**：界面卡了/慢了，判伤路径照常处理，只是显示丢旧帧；
- **处理用帧自己的参数版本**，不是"当前参数"，所以参数切换瞬间的帧不会被算错；
- **停止时账本要对平**：每条路的 `投递 = 处理 + 丢弃 + 版本未知`，且内存池没有借了不还的帧。

## 7. 三条数据路径与铁律

| 路径 | 消费者 | 队列满了怎么办 | 允许无声丢帧？ |
|---|---|---|---|
| 判伤 Inspection | 处理器 → 闸门/判据/告警 | 不覆盖旧帧，记"判伤欠帧"，会话标"检测不完整" | **绝对不行** |
| 记录 Record（M6 预留） | 存储插件 | 同上，记"记录欠帧" | **不行** |
| 显示 Display | 快照 → 界面 | 丢最旧帧，计数 | 可以，但必须计数 |

四条铁律：

1. 显示可以丢，**判伤和记录不可以无声丢**；
2. 每一帧的去向只有两种：**被某条路径处理**，或**被丢弃并记入某个原因**，没有第三种；
3. 丢帧原因必须可区分：设备溢出、序号断档、显示丢帧、判伤欠帧、参数版本未知；
4. 停止后：**未归还帧数 = 0**，否则说明有泄露（有专门的帧泄漏计数和测试）。

## 8. 为什么这样设计（目标与权衡）

| 设计 | 好处 | 代价/取舍 |
|---|---|---|
| 微内核 + 插件 | 换板卡/算法/视图不动内核；故障隔离 | 多一层接口和生命周期，代码略多 |
| 模块化单体（不是微服务） | 单进程传帧、低延迟、调试简单 | 不能横向扩展到多机（当前不需要） |
| 依赖单向、插件只认契约 | 改 UI 不碰算法；插件可独立测试 | 契约要稳定，变更要走版本/快照 |
| 控制面/数据面分离 | 参数有版本，帧可追溯；错误可定位 | 需要维护参数历史 |
| 帧池化 + 引用计数 | 减少 GC 卡顿；多条路径共享一块内存 | 所有权规则严格，借了必须还 |
| 显示快照 + 节流 | UI 不接触池化帧，慢 UI 不拖累采集 | 显示看到的不是每一帧（可接受） |
| 模拟器 + 回环板卡 | 没硬件也能开发和测试协议 | 模拟数据不能替代真实板卡联调 |
| 契约只增不改 + API 快照 | 插件升级不被破坏 | 小改动也要升版本/更新快照 |

## 9. 质量门禁：为什么有这么多测试

不是"为了测试而测试"，每条门禁都对应一类事故：

| 门禁 | 防什么事故 |
|---|---|
| 编译 0 警告（`-warnaserror`） | 警告越积越多，真问题被淹没 |
| 168 个测试 | 改一处坏另一处（回归） |
| `dotnet format --verify-no-changes` | 格式混乱、合并冲突 |
| 禁用 API 分析器 | 库代码里偷偷 `Console.WriteLine`、`.Result`、`Thread.Sleep` 导致卡死/测试污染 |
| 架构测试（R1–R11） | 新人把代码放错项目、插件反向依赖、绕过 `GetActive` |
| 契约 API 快照 | 偷偷改公共接口导致插件编译不过 |
| 插件契约套件（PG/DC/PC/VC） | 新插件"看起来能跑"但不满足设备/处理器/视图的约定 |
| 帧泄漏计数 + DP7/DP9 | 帧借了不还、异常/启停时内存泄漏 |
| 回环假板卡 + 协议往返测试 | 没硬件时协议写错，等板卡到了才发现 |

一条命令跑全部门禁：`./scripts/verify.ps1`（restore → build -warnaserror → test → format）。

## 11. 新人上手：三分钟跑起来

前置：Windows、.NET 8 SDK。

```powershell
# 1. 编译
dotnet build UltrasoundHost.sln

# 2. 跑测试（第一次会比较久）
dotnet test UltrasoundHost.sln

# 3. 无界面跑 30 帧，看输出
dotnet run --project src/UltrasoundHost.App.Cli -- --frames 30

# 4. 打开 WPF 界面
dotnet run --project src/UltrasoundHost.App.Wpf

# 5. 无桌面环境自检（不需要显示器）
dotnet run --project src/UltrasoundHost.App.Wpf -- --selftest --report out/selftest.txt

# 6. 一条命令跑全部质量门禁
./scripts/verify.ps1
```

> 如果 `dotnet test` 在受限环境报 testhost 权限错误，可以用仓库内 `.tools` 的 xunit console 跑（细节见 01 §1.13），结论与 `dotnet test` 相同。

## 13. 术语表（看不懂时回来查）

| 词 | 大白话 |
|---|---|
| 上位机 | 电脑上运行的这套软件（相对板卡上的固件/下位机） |
| 板卡/下位机 | 产生超声脉冲、接收回波的硬件 |
| FPGA | 板卡上负责高速采集/处理的芯片 |
| ADC | 模数转换器，把模拟回波变成数字；位数决定精度 |
| 采样率 | 每秒采多少个点，50 MSPS = 每秒 5000 万点 |
| PRF | 每秒发多少次超声脉冲，决定帧率 |
| A 扫 | 一条深度方向的波形（幅度随距离变化） |
| 闸门（Gate） | 在 A 扫上划一个区间，只看区间内的最高回波 |
| 峰值 | 闸门区间内的最大幅度，用来判断缺陷 |
| 相控阵 | 多个阵元按延迟发射/接收，实现聚焦和偏转 |
| TFM | 全聚焦方法，一种高级成像算法（后续里程碑） |
| 微内核 | 内核只做装配/生命周期，能力都放插件 |
| 模块化单体 | 一个进程、多个模块，模块间靠接口隔离（不是微服务） |
| 插件 | 可替换的能力模块（设备/处理/视图……） |
| 契约（Contracts） | 所有模块共用的接口和数据类型，相当于插座标准 |
| 宿主（Host） | 负责启动、停止、监控插件的组件 |
| 组合根 | 唯一负责"装配所有插件"的地方（`App.*`） |
| 帧 | 一次采集得到的一块数据（含帧头信息 + 采样点） |
| 池化 | 内存重复使用，减少分配/GC；借了必须还 |
| 引用计数 | 有多少人还在用这块帧；最后一个不用的人负责归还 |
| 快照 | 从帧拷贝出来的、给界面安全读取的只读数据 |
| 参数版本 | 每改一次采集参数 +1，帧自带版本以便追溯 |
| 丢帧计数 | 记录每一帧是处理了还是丢了、为什么丢 |
| 回环 | 板卡/假板卡自己产生数据，不接真实探头也能测链路 |
| 回放 | 把录下来的数据重新喂给软件（M6 预留） |

## 14. 常见问题（FAQ）

**Q1：为什么不用微服务？**
A：超声数据量大、延迟敏感，单机单进程传帧最快；模块化单体已经能做到"模块可替换"，不需要网络开销。

**Q2：Contracts 为什么不能引用别的项目？**
A：它是所有层的"公共语言"。如果它依赖 Core/Application，就会出现循环依赖，插件也没法独立编译。

**Q3：Core 和 Application 为什么要分开？**
A：Core 是通用插件宿主（启动/状态/故障隔离），可以复用到别的项目；Application 是超声业务编排（采集会话、分发、计数）。分开后，Core 不需要知道超声业务。

**Q4：为什么插件不能引用 WPF？**
A：插件只描述"我要什么数据/我提供什么能力"，具体怎么画由外壳决定。这样换 UI、做无界面测试、以后做 Web 端都不用改插件。

**Q5：为什么显示可以丢帧，判伤不可以？**
A：界面只要看到"最新画面"，丢几帧人眼看不出来；判伤漏一帧可能漏一个缺陷，所以判伤路径队列满必须告警并标"检测不完整"。

**Q6：为什么帧要池化、要 Retain/Dispose？**
A：一帧可能几 MB，每秒上千帧；不停 new/垃圾回收会让界面卡顿。池化 + 引用计数让多条路径共享同一块内存，最后一个人还回去。

**Q7：为什么有这么多测试？**
A：每条规则都对应一类事故（见 §9）。测试是"自动化的代码评审"，防止后来的人无意破坏架构。

**Q8：没有板卡能开发吗？**
A：能。模拟器提供假数据；`device.serial-udp` 的 `loopback=true` 提供假板卡协议；插件契约套件保证新插件符合约定。真实板卡到了只需补串口/UDP 传输并联调。

**Q9：我只想改界面，需要懂这些吗？**
A：至少要懂"界面只调用 `ShellSession`、只读快照、不碰帧"。界面代码在 `App.Wpf`，不要改 Contracts/Core/Application。

**Q10：我想加一个新算法/新板卡，从哪开始？**
A：加算法 → 新建 `Plugins.Processing.*`，实现 `IProcessorContribution` + `IFrameProcessor`；加板卡 → 新建 `Plugins.Device.*`，实现 `IDeviceFactoryContribution`。然后继承对应的契约测试基类，跑通测试，最后在 `App.*` 的装配清单里注册。详见 [01 插件约定](spec/01-plugin-conventions.md)。
