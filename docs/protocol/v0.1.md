# 协议 v0.1（草案）

状态：**草案**（2026-10-28）　对应里程碑：M3（协议 + 真实设备）

> 本文件是"先提一版"的字节级协议草案，用于回环假板卡与设备插件开发；**真实板卡/固件确认前不作对外依据**。
> 实现：`src/Plugins/UltrasoundHost.Plugins.Device.SerialUdp`（回环模式通过设备契约套件；真实串口/网口传输待硬件确认后补）。
> 字段与契约的对应关系：序号/标志见 06 §C4，ADC 见 06 §C1，实际通道数见 06 §C5。
> 需要硬件/固件提供的信息：见 [板卡信息问卷](hardware-info-request.md)；[填写示例](hardware-info-example.md)（虚构板卡）演示答到什么粒度。

## 1. 传输假设

| 通道 | 传输 | 方向 | 说明 |
|---|---|---|---|
| 控制 | 串口（全双工） | 上位机 ⇄ 板卡 | 命令/响应，一问一答；波特率、流控**待定** |
| 数据 | UDP（以太网） | 板卡 → 上位机 | 一块板卡发往一个目的端口；端口、MTU、是否 Jumbo Frame **待定** |

- 全部多字节整数为**小端序**。
- 控制通道暂时按"一问一答"设计：上位机发一条请求，等一条响应；超时重试策略待定。
- 数据通道一个 UDP 数据报承载一帧；分片/重组字段已预留，v0.1 **只允许单分片**。
- 单数据报上限按 IPv4 UDP 有效载荷 65507 字节；即 payload ≤ 65467 字节（见 §4）。

## 2. 控制通道帧

### 2.1 请求

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 2 | Magic | `AA 55`（小端 u16 = 0x55AA） |
| 2 | 1 | Command | 见 §2.2 |
| 3 | 2 | PayloadLength | u16，不含头与 CRC |
| 5 | N | Payload | 命令相关，见 §3 |
| 5+N | 2 | CRC16 | CRC-16/CCITT-FALSE（poly 0x1021, init 0xFFFF），覆盖 Command..Payload |

### 2.2 响应

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 2 | Magic | `AA 55` |
| 2 | 1 | Command | 请求命令 \| 0x80 |
| 3 | 1 | Status | 见下表 |
| 4 | 2 | PayloadLength | u16 |
| 6 | N | Payload | 命令相关 |
| 6+N | 2 | CRC16 | 覆盖 Command、Status、PayloadLength、Payload |

CRC 计算均不含 Magic 与 CRC 本身。

### 2.3 命令与状态

| Command | 值 | Payload（请求） | 响应 Payload |
|---|---|---|---|
| Identify | 0x01 | 空 | 能力声明，见 §3.1 |
| Configure | 0x02 | 采集参数，见 §3.2 | 空 |
| Start | 0x03 | 空 | 空 |
| Stop | 0x04 | 空 | 空 |

| Status | 值 | 含义 |
|---|---|---|
| Ok | 0 | 成功 |
| BadCommand | 1 | 未知命令 |
| BadChecksum | 2 | CRC 失败 |
| BadParameter | 3 | 参数非法（未配置就 Start 等） |
| Busy | 4 | 当前状态不允许该命令 |

状态机：

```
Closed/Opened ──Identify──► Identified ──Configure──► Configured ──Start──► Running
                                                                  ◄──Stop──┘
任意状态收到未知命令/坏 CRC：返回对应 Status，不改变状态
```

## 4. 数据通道帧

### 4.1 数据报头（40 字节）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | Magic | u32 = 0x544C5355（字节序 `55 53 4C 54`） |
| 4 | 2 | ProtocolVersion | u16 = 1 |
| 6 | 2 | HeaderSize | u16 = 40 |
| 8 | 8 | Sequence | u64，同一设备同一次采集严格递增、步长 1；丢包会形成空号，主机按契约计 `SequenceGaps` |
| 16 | 4 | ParamVersion | u32，与产生本帧的 Configure.Version 一致 |
| 20 | 2 | Tx | u16，AScan 固定为 1 |
| 22 | 2 | Rx | u16，接收通道数 |
| 24 | 4 | Samples | u32，每通道采样点数 |
| 28 | 1 | AdcBits | u8 |
| 29 | 1 | AdcFlags | bit0=有符号，bit1=右对齐 |
| 30 | 1 | FrameFlags | bit0=DeviceOverflow（设备侧丢过数据），bit1=Truncated（本帧不完整） |
| 31 | 1 | Reserved | 置 0 |
| 32 | 2 | FragmentIndex | 预留，v0.1 固定 0 |
| 34 | 2 | FragmentCount | 预留，v0.1 必须为 1 |
| 36 | 4 | Checksum | CRC-32/ISO-HDLC，覆盖偏移 0..35 与整个 Payload（不含本字段） |
| 40 | N | Payload | int16 小端，按 `[tx][rx][sample]` 连续排列，N = Tx×Rx×Samples×2 |

约束：

- Payload 必须恰好占满数据报剩余部分；长度不符、Magic/版本/头长/CRC 不符的报文由设备插件**丢弃**，主机侧随后的序号空号会体现丢帧。
- 数据报大小不超过 65507 字节；更大的帧需要分片，分片/重组**待硬件 MTU 与最大帧确认后**在 v0.2 定义。
- 序号回退或重复由主机视为设备错误（契约 06 §C4）；数据报乱序是否接受、重排序窗口多大，**待固件实现确认**。
- 设备侧 FIFO 溢出：把 `FrameFlags.DeviceOverflow` 置在溢出后的第一帧上（语义由 06 §C4 定义）。

| 契约字段 | 协议字段 |

## 7. 需要硬件/固件确认的问题

1. 控制口参数：波特率、数据位/停止位/校验、流控、命令超时与重试。
2. 数据口：UDP 目的/源端口、是否允许 Jumbo Frame、MTU、发送速率上限。
3. 板卡能力：采样位数（12/14/16）、最高采样率、单帧最大采样点、板上 FIFO 深度。
4. 序号与溢出：序号由 FPGA 还是软件赋值；溢出标志的置位语义与重同步方式。
5. 数据报乱序/重复的处理策略；是否需要序号确认或重传（UDP 无重传时仅计数）。
6. 校验方式是否可改为硬件 CRC 或以太网 FCS 复用。

以上确认后，协议升级为 v0.1 定稿并更新本文与插件实现。
