# 05 数据通路与丢帧计数

状态：**已确认**（2026-10-28）　日期：2026-10-28
对应工作包：WP4、WP5
背景：现有 `ShellSession` 用一个 `DropOldest` 通道、一个泵同时服务判伤和显示，被丢的帧只 `Dispose`，不计数。探伤软件里，一帧没判就是一个可能漏报的缺陷，所以必须把“可丢”和“不可丢”拆开，并让每一次丢弃都可追溯。

## 1. 原则

- **P1** 显示可以丢，判伤和记录不可以无声丢。
- **P2** 每一帧的去向只有两种：被某条路径处理，或被丢弃并记入某个原因的计数。没有第三种。
- **P3** 丢弃的原因必须可区分：设备侧、序号断档、显示丢帧、判伤欠帧、记录欠帧、参数版本未知。
- **P4** 判伤路径一旦有欠帧，会话状态变为“检测不完整”，界面必须显示，且写入后续记录。
- **P5** 帧用哪一版参数处理，由帧自带的 `ParamVersion` 决定，不靠“当前参数”猜。

## 2. 三条路径

| 路径 | 消费者 | 队列满时 | 计数 | 告警 |
|---|---|---|---|---|
| 判伤（Inspection） | 处理器 → 闸门/判据/告警 | **不覆盖旧帧**；新帧入队失败 → 记 `InspectionOverrun` | 每帧必计 | 是：会话置“检测不完整” |
| 记录（Record） | 存储插件（M6，预留） | 同上，记 `RecordOverrun` | 每帧必计 | 是 |
| 显示（Display） | 显示快照 → UI | 丢最旧（`DropOldest`），记 `DisplayDropped` | 每帧必计 | 否（仅统计） |

队列容量：判伤、记录路径默认比显示大一个数量级，且可在 `SessionOptions` 调整。队列满意味着处理跟不上采集，是需要被看见的故障，不是正常现象。

## 3. 分发（FrameFanout）

唯一读者从设备通道取帧，对每个启用的路径执行：

```
对每个消费者 c：
    frame.Retain()                      // F2
    若 c.Queue.TryWrite(frame) 失败：
        frame.Dispose()                  // 归还这次 Retain（F4）
        计数(c, 该路径的丢弃原因)
最后 frame.Dispose()                    // 释放分发自己持有的那一份
```

要点：
- 分发任务本身不做任何处理，只做序号检查、计数与入队，耗时恒定。
- 显示队列用 `itemDropped` 回调释放被挤掉的帧并计数；判伤、记录队列不使用 `DropOldest`。
- 帧的所有权规则 F1–F4 不变；本文件只增加“谁持有、谁释放”的分发实例。

## 4. 序号与断档

- `AcquisitionFrame.Sequence` 在同一设备同一次采集内严格递增、步长 1（06 §C4 写入契约）。
- 分发在入口检查：`gap = seq − last − 1`，`gap > 0` 记入 `SequenceGaps`（含丢失帧数）。设备侧自己上报的溢出（帧标志 `DeviceOverflow`）记入 `DeviceOverflow`。
- 序号回退或重复视为设备错误：记 `SequenceViolations`，并置会话错误。
- 断档属于**设备/链路丢帧**，与主机队列丢帧分开计数，便于定位是板卡、网络还是主机的问题。

## 5. 计数与不变量

`LossCounters` 为线程安全的只读快照对象，字段（按路径和原因分开）：

| 字段 | 含义 |
|---|---|
| `Received` | 分发收到的帧数 |
| `SequenceGaps` | 序号断档丢失的帧数 |
| `DeviceOverflow` | 设备上报溢出的帧数 |
| `Offered[path]` | 向某路径投递的帧数 |
| `Processed[path]` | 某路径处理完成的帧数 |
| `Dropped[path]` | 某路径入队失败或被挤掉的帧数 |
| `UnknownVersion[path]` | 参数历史里找不到该版本而丢弃的帧数 |

不变量（测试里断言）：

1. 每一帧对每条启用的路径恰好投递一次：`Offered[p] = Received`。
2. 停止并排空后：`Offered[p] = Processed[p] + Dropped[p] + UnknownVersion[p]`。
3. 停止后帧池中未归还的帧数为 0（07 的泄漏计数）。
4. 判伤路径：`Dropped[Inspection] + UnknownVersion[Inspection] > 0` ⇔ 会话状态“检测不完整”。

## 6. 参数历史（ParameterHistory）

- `ApplyParametersAsync` 在把参数写入设备**之前**先登记到历史，再应用；这样在设备切换版本的瞬间，带新版本号的帧到达时历史里已有它。
- 历史保留最近 N 个版本（默认 16，可配置），按版本号索引；处理时用 `frame.ParamVersion` 查表。
- 查不到（版本太旧或设备给了不存在的版本）→ 记 `UnknownVersion`，判伤路径视同欠帧。
- 取代现有做法：现在 `frame.ParamVersion != current.Version` 就丢弃（计入 `StaleDropped`），改参数的瞬间在途帧会被白白丢掉，对判伤路径是无谓的欠帧。
- 参数仍是不可变对象且版本严格递增（契约规则不变）。
- 兼容：原 `StaleDropped` 属性保留一个版本周期后移除，其值恒为 `UnknownVersion` 之和。

## 7. 显示取数（WP5）

目标：多通道、FMC 时，UI 不因快照而成为瓶颈。

- 视图通过 `ViewDescriptor.Needs`（06 §C3）声明需要什么：哪些通道（全部/指定/仅当前选中）、横向最多多少点、每秒最多刷新多少次。默认值等于现有行为（全部通道、不抽取），因此对现有视图兼容。
- 会话把当前激活视图的需求取并集，形成 `DisplayRequest`；显示消费者只按它拷贝。
- **抽取必须保峰值**：把相邻 K 个采样替换为其最小值与最大值两点（或等价的包络），不得用跳采样，否则尖峰（可能是缺陷回波）会消失。抽取只用于显示，判伤始终用完整数据。
- 快照缓冲来自池（`ArrayPool<short>`），快照实现 `IDisposable` 或由“最新快照”槽位双缓冲复用，避免每帧分配；UI 取到的快照在其被替换前保持有效（用引用计数或不可变拷贝实现，具体写在实现中，要求：UI 线程读到的数据不会被后台线程改写）。
- 刷新频率由显示消费者按视图需求节流，不是每帧都拷贝。

## 8. 停止顺序

1. 取消采集令牌，要求设备 `StopAsync`（设备停止后不得再写通道）。
2. 完成设备通道写端，分发排空剩余帧并投递。
3. 各路径队列完成写端，等待各消费任务处理完毕（带超时；超时则记错误并强制释放剩余帧）。
4. 排空并 `Dispose` 所有未处理的帧；断言池中未归还数为 0。
5. 输出最终计数快照（供记录与界面）。

停止的每一步都带超时，UI 退出路径不得无限阻塞。

## 9. 测试清单（WP4/WP5 验收）

| 编号 | 场景 | 断言 |
|---|---|---|
| DP1 | 正常速率，三条路径 | 无丢弃；不变量 1、2 成立 |
| DP2 | 显示消费者故意变慢 | `DisplayDropped > 0`，判伤路径无丢弃，无告警 |
| DP3 | 判伤消费者故意变慢且队列小 | `Dropped[Inspection] > 0`，会话“检测不完整” |
| DP4 | 模拟器注入序号断档 | `SequenceGaps` 等于注入数量 |
| DP5 | 运行中改参数 | 在途帧用其自带版本处理，`UnknownVersion = 0` |
| DP6 | 设备给出未知版本号的帧 | 记 `UnknownVersion`，判伤欠帧 |
| DP7 | 运行中停止、设备异常、消费者异常 | 无死锁；池中未归还为 0；错误可读取 |
| DP8 | 多通道（如 16）快照 | 只拷贝请求的通道；抽取后尖峰仍在（峰值保持） |
| DP9 | 重复启动停止 100 次 | 无泄漏、无线程残留 |
