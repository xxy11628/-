# 08 路线图（M3 之后）

状态：**已确认**（2026-10-28）　日期：2026-10-28
说明：本文是方向与进入/退出条件，不是排期。工作量未估算，因为依赖的板卡信息、阵列规模、人力都还没定；每个里程碑开始前再写细则。各里程碑的名称沿用 03 的编号（M0–M2 已定义）。

## 总览

| 里程碑 | 主题 | 开始前必须确定 | 退出标志 |
|---|---|---|---|
| M3 | 协议 v0.1 + 真实设备（串口控制 + 以太网数据） | 板卡/固件状态、D6 采样率与 PRF 约束 | 真实或回环板卡跑通整条链，长时间无未解释的丢帧 |
| M4 | 相控阵：聚焦法则 + 主机 CPU 波束合成 | D3 并行通道数、D5 FPGA 分工 | S 扫成像，CPU 结果与参考一致，黄金向量建立 |

## M3 协议 v0.1 与真实设备

**目标**：定义上位机与板卡之间的字节级协议，并实现第一个真实设备插件。

**先决问题**（需要你提供，没有它们协议只能“我们先提一版”）：
- 固件是否已在跑？有无现成命令或数据格式？
- 板卡采样位数、最高采样率、单帧最大点数、板上缓存深度、是否有触发/编码器输入？
- 数据口是 UDP 还是 TCP？是否有 DMA/网卡限制？

**交付**：
1. `docs/protocol/v0.1.md`：控制通道（串口）命令表、响应与错误码、状态机；数据通道（以太网）帧头字段（魔数、协议版本、序号、参数版本、通道/阵元信息、采样数、ADC 格式、标志位、校验）、字节序、分片与重组、丢包语义。字段要与 06 的契约一一对应（序号、标志、ADC）。
2. `Plugins.Device.SerialUdp`：串口与网口两个传输各自是可替换的小接口，设备插件组合它们；PCIe 以后只是再加一个传输。
3. **回环假板卡**（独立小程序或测试内对象）：按协议发数据，支持注入丢包、乱序、延迟，使协议和插件在没有硬件时就能被测试。
4. 通过 07 的设备契约测试套件。

**退出条件**：回环下连续运行一段规定时长（例如数小时）无未解释的序号断档；注入各类故障时，丢帧计数与注入一致；接上真实板卡后同样通过。

**风险**：真实板卡与协议文档不一致；以太网吞吐与主机接收缓冲不足。对策：协议里留版本字段、先用回环，再用真实板卡逐项对照。

**进展（2026-10-28）**：协议 v0.1 草案已写入 `docs/protocol/v0.1.md`；`Plugins.Device.SerialUdp` 插件骨架与回环假板卡已实现，回环设备通过设备契约套件（DC1–DC9）与会话端到端；真实串口/UDP 传输与协议参数仍待第 7 节的硬件/固件问题确认。回环板支持丢包/坏包注入，用于验证序号断档与丢帧计数。需要硬件/固件回答的问题整理成了 [板卡信息问卷](../protocol/hardware-info-request.md)，并附 [填写示例](../protocol/hardware-info-example.md)（虚构板卡）供非专业同事照格式填写。

## M4 相控阵与主机 CPU 波束合成

**目标**：线阵 PA，发射聚焦法则 + 接收延时叠加，输出 `BeamformedLine`，有 S 扫视图。

**交付**：
- `ProbeModel` 生成器（线阵、环阵、曲面；面阵留接口）。
- 聚焦法则计算（扇扫、线扫、偏转角、聚焦深度），含楔块/界面折射的可扩展点。
- `IBeamformer` 的两个实现：`HardwareBeamformerPassthrough`（板上 FPGA 已合成，直接透传）和 `HostCpuBeamformer`（含“逐位对齐 FPGA”模式）。
- 一个延时叠加核既用于 PA 也将用于 TFM，接口里不分开。
- “原始 + 合成”双模式：同时保留原始通道数据与合成线，用于验证 FPGA。
- **黄金测试向量**：给定输入与法则，固定的输出；FPGA 开发方用同一批向量验证自己的实现。
- S 扫视图插件（走 `IViewContribution`，按 06 §C3 声明取数需求）。

**退出条件**：CPU 实现与独立参考（可用 Python 参考实现或开源参考，许可证需先核实）一致；黄金向量固化并纳入测试。

**待核实**：开源参考实现的许可证（例如 arim 的上游许可证未核实；USTB/UFF 未找到许可证）。GPLv3 的软件（如 un0rick）只借鉴思路，不拷贝代码。

## M5 GPU 波束合成

**目标**：用 ILGPU（许可证 NCSA，使用前仍需自行确认）或同类库，在 NVIDIA GPU 上实现同一接口。

**交付**：
- `HostGpuBeamformer`；与 CPU 版共用同一套测试。
- 性能预算文档：阵元数、采样点数、扇扫线数、PRF 下每帧的耗时上限；基准程序。
- GPU 不可用时自动回退到 CPU 版并明确提示。

**退出条件**：满足性能预算；与 CPU 结果在规定容差内一致；GPU 异常不影响判伤路径的帧归还与计数。

**注意**：数据量大时 GPU 拷贝成为瓶颈，需要在预算里把“主机到设备拷贝”算进去；这部分估算要在拿到真实阵列规模后重做。

## M6 FMC/TFM、记录回放、检测工艺

**目标**：全矩阵采集与全聚焦成像；记录与回放；把检测方法组织成工艺。

**交付**：
- 大帧分块：解除 `Rent` 对超过单数组上限帧的 `NotSupportedException`（例如 1024×1024×4096 样本的情形），帧以“块序列”表示，消费者按块处理。
- `Plugins.Storage.*`：记录路径的消费者。文件格式在此阶段决定：候选是 HDF5（与 UFF 对应，便于与学术工具互通；UFF 许可证未核实），或自定义的分块二进制 + 元数据。选型前写一页对比。
- `Plugins.Device.Replay`：回放设备，让记录的数据走同一条链路。它既是复核功能，也是回归测试的基础。
- `ITechniquePlugin`：检测工艺（设备配置 + 处理链 + 视图 + 判据）作为可选择、可保存的对象。
- TFM 视图与处理。

**退出条件**：同一份记录回放后，判伤结果与录制时一致；TFM 在已知试块上成像正确。

## M7 产品化

**范围**：校准向导（声速、延迟、增益）、报告生成、权限与审计日志、安装包、操作员与维护两级界面。

**标准**：目标是“需要符合行业标准”。目前**没有已核实的标准清单**。我记得可能相关的有国内承压设备无损检测（NB/T 47013 系列）、超声仪器性能的国标/行标，以及 EN 12668、ISO 18563、ASTM 的相关部分，但这些全凭记忆，未核实，不可当依据。

做法：
1. 你确定目标市场（国内/出口）与应用行业。
2. 取得标准的现行有效版本（可能需要购买），逐条摘出**软件相关**条款（例如：数据完整性、校准记录、报告内容、仪器线性度/分辨力的测量方式、文件追溯）。
3. 形成“标准条款 → 软件需求 → 测试”的追溯表，放进 `docs/standards/`。
4. 其中会反推到前面里程碑的要求，因此**在 M4 之前**至少应完成第 1 步和第 2 步的初稿，否则 M7 可能要返工契约。

## 横向主题

| 主题 | 现在已留好什么 | 何时处理 |
|---|---|---|
| 1024+ 阵元/面阵 | `ProbeModel` 为位置列表；帧形状含 Tx、Rx；能力用范围与标志而非固定数 | M6 的分块，M4 起生成器支持面阵 |
| 多板/多通道同步 | `DeviceCapabilities` 的多板同步声明；会话允许多设备的接口空间 | 有第二块板卡时 |
| 动态加载与隔离 | 清单不假设来自本进程；R3、R4 保证无程序集耦合 | 出现第三方/客户插件需求时（加载上下文、权限、崩溃隔离） |
| FPGA 版波束合成 | `IBeamformer` 与透传实现；黄金向量 | M4 起与 FPGA 开发同步 |
| 数据安全与追溯 | 参数版本、序号、丢帧计数 | M6 记录格式里带上全部这些元数据 |
